## Conversation identity (CRITICAL)

The recon report called this `conversation_token`. **The actual field is `conversation_id`** (string, in `Request.Metadata.conversation_id` request.proto:321 / `ResponseEvent.StreamInit.conversation_id` response.proto:41). All references in the plan to `conversation_token` must be `conversation_id`.

- **First turn:** client sends `metadata.conversation_id = ""`. Server (or our backend) mints a new id and returns it in `StreamInit.conversation_id`.
- **Follow-up turns:** client sends the same `conversation_id`.
- Our `ConversationStore` is keyed on this string.

## Inbound: how to extract the user's prompt

`Request.input` is a `oneof type` with 14 variants (request.proto:53–71). For v0.1 we handle two:

```
Request
└─ input: Input
   └─ type: oneof
      ├─ user_inputs: UserInputs                         ← v0.1 supports
      │  └─ inputs: repeated UserInput                   ← can be many in one turn
      │     └─ input: oneof
      │        ├─ user_query: UserQuery                  ← `query: string` is the user's text
      │        ├─ tool_call_result: ToolCallResult       ← `tool_call_id` + `result: oneof`
      │        ├─ cli_agent_user_query                   ← v0.1: error
      │        ├─ messages_received_from_agents          ← v0.1: error
      │        ├─ events_from_agents                     ← v0.1: error
      │        └─ passive_suggestion_result              ← v0.1: error
      ├─ query_with_canned_response                      ← v0.1: error
      ├─ auto_code_diff_query                            ← v0.1: error
      ├─ resume_conversation                             ← v0.1: error
      ├─ init_project_rules                              ← v0.1: error
      ├─ generate_passive_suggestions                    ← v0.1: error
      ├─ create_new_project                              ← v0.1: error
      ├─ clone_repository                                ← v0.1: error
      ├─ code_review                                     ← v0.1: error
      ├─ summarize_conversation                          ← v0.1: error
      ├─ create_environment                              ← v0.1: error

      └─ invoke_skill                                    ← v0.1: error
```

For "v0.1: error" variants the translator emits `StreamFinished { internal_error: { message: "<variant> not yet supported by llama_backend" } }` and stops.

## Settings.supported_tools

`Request.settings.supported_tools` (repeated `ToolType`, request.proto:374) tells us which tools the *client* can actually execute. The server (us) MUST only emit tool calls in this list. The `ToolType` enum is in task.proto:1547–1580 with 32 variants (`RUN_SHELL_COMMAND = 0`, …, `UPLOAD_FILE_ARTIFACT = 31`).

Our outbound translator filters the OpenAI `tools` list to the intersection of (our registry) ∩ (`supported_tools`).

## MCP tools (dynamic)

`Request.mcp_context.servers` (repeated `MCPServer`, request.proto:493) carries each connected MCP server's `id`, `name`, `description`, `tools` (each `{name, description, input_schema:Struct}`), and `resources`.

Translator merges these into the OpenAI `tools` list at request time, naming each as `mcp__<server_id>__<tool_name>` so the response translator can recognize them and route to `Tool::CallMCPTool { name: <tool_name>, args: <Struct from JSON args>, server_id }`.

## Outbound: what events we emit per turn

The complete stream the client expects per turn, from `dispatch_if_enabled` returning a stream:

```
ResponseEvent { init: StreamInit {
    conversation_id: <minted or echoed>,
    request_id:      <uuid>,
    run_id:          <uuid>,
} }
ResponseEvent { client_actions: ClientActions { actions: [
    ClientAction { begin_transaction: BeginTransaction {} }
] } }
ResponseEvent { client_actions: ClientActions { actions: [
    ClientAction { create_task: CreateTask {
        task: Task { id: <task_uuid>, description: "Agent Mode" }
    } }
] } }
ResponseEvent { client_actions: ClientActions { actions: [
    ClientAction { add_messages_to_task: AddMessagesToTask {
        task_id: <task_uuid>,
        messages: [ Message {
            id: <msg_uuid>,
            agent_output: AgentOutput { text: "" }   // empty seed
        } ]
    } }
] } }
// Per text delta from llama-server (after dropping reasoning_content
// and stripping leading "</think>\s*" from the first delta):
ResponseEvent { client_actions: ClientActions { actions: [
    ClientAction { append_to_message_content: AppendToMessageContent {
        task_id: <task_uuid>,
        message: Message { id: <msg_uuid>, agent_output: AgentOutput { text: <delta> } },
        mask: FieldMask { paths: ["agent_output.text"] }
    } }
] } }
// At finish_reason="tool_calls", per tool call:
ResponseEvent { client_actions: ClientActions { actions: [
    ClientAction { add_messages_to_task: AddMessagesToTask {
        task_id: <task_uuid>,
        messages: [ Message {
            id: <new_msg_uuid>,
            tool_call: ToolCall {
                tool_call_id: <openai-call-id>,
                run_shell_command: ToolCall::RunShellCommand { command: "<cmd>" }  // or whichever tool
            }
        } ]
    } }
] } }
// At end of stream:
ResponseEvent { client_actions: ClientActions { actions: [
    ClientAction { commit_transaction: CommitTransaction {} }
] } }
ResponseEvent { finished: StreamFinished { done: Done {} } }   // or appropriate variant
```

## Tools we will support in v0.1 (hard-coded OpenAI schemas)

These are the seven we expose as OpenAI function-defs by default (intersected with `Settings.supported_tools` and merged with MCP tools). Field paths in the parens are the proto path of the tool and its result.

1. **`run_shell_command`** — `ToolCall.run_shell_command` (task.proto:407, `RunShellCommand { command, is_read_only, uses_pager, is_risky, wait_until_complete, risk_category }`); result `ToolCallResult.run_shell_command` (task.proto:1093, `RunShellCommandResult { command, result: oneof { long_running_command_snapshot, command_finished:{output, exit_code, command_id}, permission_denied } }`).
2. **`read_files`** — `ToolCall.read_files` (task.proto:475, `ReadFiles { files: [{name, line_ranges}] }`); result `ToolCallResult.read_files` (task.proto:1119) `oneof { text_files_success:{files: [FileContent]}, any_files_success, error:{message} }`.
3. **`search_codebase`** — `ToolCall.search_codebase` (task.proto:485); result `task.proto:1134`.
4. **`apply_file_diffs`** — `ToolCall.apply_file_diffs` (task.proto:494, `ApplyFileDiffs { summary, diffs:[{file_path,search,replace}], new_files:[{file_path,content}], deleted_files:[{file_path}], v4a_updates }`); result `task.proto:1146`. v0.1 uses the simple `diffs` + `new_files` + `deleted_files` shape; ignore v4a in the OpenAI schema.
5. **`grep`** — `ToolCall.grep` (task.proto:559, `Grep { queries:[string], path:string }`); result `task.proto:1193`.
6. **`file_glob_v2`** — `ToolCall.file_glob_v2` (task.proto:575, `FileGlobV2 { patterns:[string], search_dir, max_matches, max_depth, min_depth }`); result `task.proto:1237`.
7. **MCP tools (dynamic)** — `ToolCall.call_mcp_tool` (task.proto:600, `CallMCPTool { name, args:google.protobuf.Struct, server_id }`); result `task.proto:1339`. Generated at runtime from `Request.mcp_context.servers[].tools[]`.

Tools we do **not** expose in v0.1 (the model can't pick them, even if `Settings.supported_tools` lists them): every other `ToolType` variant (suggest_plan, suggest_create_plan, write_to_long_running_shell_command, suggest_new_conversation, suggest_prompt, open_code_review, init_project, subagent, read_documents, edit_documents, create_documents, read_shell_command_output, use_computer, insert_review_comments, read_skill, request_computer_use, fetch_conversation, start_agent, send_message_to_agent, transfer_shell_command_control_to_user, ask_user_question, start_agent_v2, upload_file_artifact). They are deliberately scoped out.

## Tool-result deserialization (Phase 9)

`Request.input.user_inputs.inputs[i].tool_call_result` is a `ToolCallResult` (request.proto:144) with `tool_call_id` (1) and `oneof result` carrying one of 30+ result variants. Each maps to a JSON we feed back as the `tool` role's `content` in the OpenAI conversation. Examples (full table in tool_registry.rs):

| Variant | JSON shape we serialize for the model |
|---|---|
| `run_shell_command` | `{"command":..., "exit_code":N, "stdout":"…", "stderr":""}` (from `ShellCommandFinished`) or `{"long_running":true, "command_id":"…"}` or `{"permission_denied":true}` |
| `read_files` | `{"files":[{"path":"…","content":"…"}], "error": null}` or `{"error":"…"}` |
| `search_codebase` | `{"files":[{"path":"…","content":"…"}]}` or `{"error":"…"}` |
| `apply_file_diffs` | `{"updated_files":[…], "deleted_files":[…]}` or `{"error":"…"}` |
| `grep` | `{"matches":[{"path":"…","lines":[N,…]}]}` or `{"error":"…"}` |
| `file_glob_v2` | `{"matched_files":["…"], "warnings":"…"}` or `{"error":"…"}` |
| `call_mcp_tool` | `{"results":[{"text":"…"} | {"image":{"mime":"…","b64":"…"}} | {"resource":{"uri":"…","mime":"…","content":"…"}}]}` or `{"error":"…"}` |

Other variants in v0.1: serialize as `{"unhandled_variant":"<name>"}` so the model gets *something* back rather than hanging.

## Stream finished — error mapping

`StreamFinished.reason` is a `oneof` (response.proto:62–71) of: `Other`, `Done`, `ReachedMaxTokenLimit`, `QuotaLimit`, `ContextWindowExceeded`, `LLMUnavailable`, `InternalError { message }`, `InvalidApiKey { provider, model_name }`. Map our `LlamaBackendError`:

| Our error | StreamFinished variant |
|---|---|
| transport / connection refused | `LLMUnavailable {}` |
| HTTP 401/403 | `InvalidApiKey { provider: LLM_PROVIDER_UNKNOWN, model_name: <model> }` |
| HTTP 4xx / 5xx other | `InternalError { message: <body excerpt> }` |
| serde parse failure on chunk | `InternalError { message: "bad chunk: <err>" }` |
| llama-server reports `finish_reason: "length"` | `ReachedMaxTokenLimit {}` |
| `finish_reason: "stop"` (normal end) | `Done {}` |

## Auth note

The protocol's `Authorization: Bearer <firebase-id-token>` is checked at `app.warp.dev`'s edge. **Our local backend is reached *before* that header is attached** (because we short-circuit at `app/src/server/server_api.rs:1091`, before the HTTP `request.bearer_auth(...)` call further down). We pass our own `WARP_LLAMA_API_KEY` to llama-server. The Firebase token is irrelevant to llama_backend.

## Reasoning content (Phase 0.4 finding)

Qwen3.6 streams `delta.reasoning_content` deltas before any `delta.content`, then leaks `</think>\n\n` into the *first* `delta.content` chunk. Translator MUST drop reasoning_content entirely (no `AgentReasoning` Message emitted — Warp's UI surface for that is unclear in v0.1) and strip leading `</think>\s*` from the first content delta via stateful flag. See plan Phase 7.
